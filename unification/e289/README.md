# E-289: the unified build against the earlier build's final state, on the same host

The question (the user, 2026-11-08): "compare the speed of the new version to the final speed that the previous version achieved." The registry row: [`writeup/record/experiments.md`](../../../writeup/record/experiments.md), E-289.

## How to run

```bash
export PYENV=<a Python with pandas 3.0.6 and matplotlib 3.11.2>
bash run.sh f-early 3; bash run.sh f-unified 3; bash run.sh py-app 3        # the goal's task, form (f)
bash run.sh forks-early 3; bash run.sh forks-unified 3; bash run.sh forks-py 3   # the forks' REPL session
bash run.sh d-unified 3                                                      # TDE + TraitMakie, setting D
```

- Each part runs a discarded warm-up (`w`) and then the runs, one fresh process each, one job at a time, niced. The forks' parts call `forks*/scripts/measure_session.sh`, which has no warm-up: its first run is discarded here.
- The earlier build needs its environments resolved and precompiled once on the host (`TraitReport/env_f`, `forks/env_forks`; done 2026-11-08 offline with julia-1.13). Setting D on the unified build uses `env_d_unified/` here, over the `-unified` siblings.
- The user asked, during the run, not to run the old version again where the source of a difference is already clear. So the earlier build ran only for the goal's task, which had never run on it, and for the forks' session, whose steps after the imports had no explanation. TraitReport (t) and NetworkDynamics' workload are compared from their recorded runs.
